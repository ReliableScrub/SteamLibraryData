# Steam Backlog DB Project — Progress Report

## Current Phase

This stretch focused on **Phase 3 reliability/performance work**, especially the data updater and HowLongToBeat integration.

Main goals:

- keep large-library UI operations responsive
- make background updates safe
- make HLTB data trustworthy
- avoid silently saving bad fuzzy matches
- give ambiguous HLTB results a manual review path

## Large-Library UI

The library table was moved to:

- `QTableView`
- custom `GameTableModel`

This fixed the major slowdown when sorting/loading a library of roughly 3,800 games.

HLTB display was also made explicit with a metric selector:

- Main Story
- Main + Extra
- Completionist
- All Styles

Relevant code:

- `Game.hltb_time()`
- `GameTableModel.set_hltb_metric()`
- `MainWindow.current_hltb_time()`
- `MainWindow.apply_filters()`

The selected metric now affects the table, sorting, filtering, details panel, and random-game picker.

## Background Update Architecture

Workers now **fetch data only**. The GUI/main thread applies results and writes SQLite.

Relevant pieces:

- `ResultBatchWorker`
- `ConcurrentResultWorker`
- `MainWindow.start_result_update()`
- `MainWindow.handle_hltb_result()`
- `MainWindow.handle_metadata_result()`
- `MainWindow.handle_achievement_result()`

HLTB concurrency is currently kept at **1 worker** while request reliability is monitored.

## SteamSpy Fixes

Full-library testing exposed inconsistent API fields.

Examples:

- `genre` can exist but be `null`
- `tags` can arrive in an unexpected format
- some JSON failures are transient

Normalization was added so these cases no longer break `save_game()`.

## HLTB Request Reliability

`search_hltb()` now distinguishes:

- `None` → request failure
- `[]` → successful request with no candidates

Request failures use retry/backoff and remain unchecked if all attempts fail.

This prevents temporary HLTB failures from being permanently saved as missing data.

## HLTB Matching

The original matcher trusted similarity too much.

A major failure case was:

`Total War: MEDIEVAL II - Definitive Edition`

matching near-perfectly to:

`Total War: MEDIEVAL III`

Similarity is now used mainly for **ranking candidates**, not proving identity.

Safe matching uses:

- `normalize_title()`
- `title_tokens()`
- `find_safe_match()`

Automatic matches require normalized title equality or equivalent token sets.

## HLTB Query Cleanup

`build_hltb_queries()` creates safe alternate searches for common Steam/HLTB naming differences.

Handled cases include:

- `™`, `®`, `©`
- literal `(TM)`
- `&` vs `and`
- trailing years
- `(Classic, 2005)` labels
- `Single Player`
- `(Classic)`
- edition/storefront suffixes
- Arabic number ↔ Roman numeral
- one-colon title reversal

Examples:

`Total War: MEDIEVAL II`
→ `MEDIEVAL II: Total War`

`Star Wars: Battlefront 2 (Classic, 2005)`
→ `Star Wars: Battlefront II (2005)`

`Mafia II (Classic)`
→ `Mafia II`

`Governor of Poker 2: Premium Edition`
→ `Governor of Poker 2`

`clean_generated_query()` removes dangling `:`, `-`, `–`, `—`, or `|` left behind by suffix removal.

Suffix patterns are ordered **most specific first** so `Steam Special Edition` is not partially stripped as only `Special Edition`.

## HLTB Review System

Some Steam/HLTB names are too different to safely auto-match.

Examples:

- `Spelunx` → `Spelunx and the Caves of Mr. Seudo`
- `Hector: Ep 1` → full `Hector: Badge of Carnage` episode title
- package names such as Empire at War Gold Pack
- DLC-heavy searches such as `Risen 2 - Dark Waters`

The HLTB state model now distinguishes:

- `matched`
- `review`
- `no_match`
- pending (`hltb_checked == False`)

Broader searches are generated by:

- `build_review_queries()`
- `add_base_title_queries()`

These can discover candidates but **cannot auto-accept them**.

## HLTB Persistence

`Game` now stores:

- `hltb_game_id`
- `hltb_web_link`
- `hltb_match_status`

SQLite also stores review candidates in `hltb_candidates`.

Relevant database helpers:

- `replace_hltb_candidates()`
- `load_hltb_candidates()`
- `clear_hltb_candidates()`

This lets the review UI work from saved candidate data instead of repeatedly querying HLTB.

## HLTB Result Application

`get_hltb_data()` now returns a structured result:

```text
matched
review
no_match
```

`game_updates.py` applies those through:

- `apply_hltb()`
- `apply_hltb_candidate()`
- `mark_hltb_no_match()`

Request failures still raise and leave the game retryable.

## Review UI

Relevant GUI functions:

A layout bug caused HLTB controls to overlap because they were added to the `QGridLayout` twice. The duplicate additions were removed and the two HLTB buttons now share a horizontal row.

## Important HLTB Bug Fixed

A refactor briefly built safe HLTB queries but never searched them.

That caused ordinary titles such as `Gemini Rue`, `Dead Island`, and `Sanctum` to immediately become `no_match`.

`get_hltb_data()` was fixed to run in this order:

1. search safe queries
2. auto-accept strict safe matches
3. keep ambiguous candidates
4. search broader review-only queries
5. return `review` if candidates exist
6. return `no_match` only if nothing useful was found

## Batch Visibility

`Update HLTB Data` currently processes:

```text
BATCH_SIZE = 5
```

unchecked games at a time.

`update_hltb_batch()` now prints the exact batch before running so each button press is visible in the terminal.

## Current State

The HLTB system is now good enough to run across the database and audit afterward instead of tuning every title individually.

Current behavior:

- safe matches are accepted automatically
- ambiguous results are saved for review
- request failures remain retryable
- real no-result entries can become `no_match`
- accepted mappings persist with HLTB ID/page information
